## 1. 问题核实结果

以下全部经 Playwright 实测，不是推测。

| # | 反馈 | 核实结果 | 性质 |
|---|---|---|---|
| 1 | 引用处看原文不便 | 检索调试最终结果**点不动**；聊天引用点开只有 240px Inspector 且**无原文** | 设计缺陷 |
| 2 | 记录页只有下半部分能滚、字体小 | `viewScrollable: false`，仅 `.results` 可滚，**可滚高度 339px / 1000px**；摘要字号 12px | **可用性倒退** |
| 3.1 | 编辑页左侧冗余红线 | `.md-editor:focus-within` 的 3px `box-shadow` 包住整个编辑器 | **真实 bug** |

## 2. 布局决策：图谱与文档阅读解耦

### 2.1 当前布局的根因

```
┌──────────────────────────────────────────────────────────┐
│ ChatView (1276px)                                        │
│ ┌─────────────────────┬────┬───────────────────────────┐ │
│ │ 对话 812px          │刻度│ 图谱面板 340px            │ │
│ │                     │40px│ ┌───────────────────────┐ │ │
│ │                     │    │ │ canvas 327 × 614      │ │ │
│ │                     │    │ │  ┌─────────────────┐  │ │ │
│ │                     │    │ │  │ Inspector 240px │  │ │ │ ← 只剩 87px 看图
│ │                     │    │ │  └─────────────────┘  │ │ │
│ │                     │    │ └───────────────────────┘ │ │
│ └─────────────────────┴────┴───────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

**根本问题不是「图谱太小」**，而是 **Inspector 被嵌在图谱面板内部**（`.graph-pane :deep(.ins) { width: 240px }`）。
文档阅读器被限制在一个 340px 容器里，无论怎么调整都是挤。

### 2.2 解法：三层分离，各自独立定尺寸

**核心洞察**：「看图」与「读文档」是两种不同的活动，不该共享同一个空间预算。

```
┌────────────────────────────────────────────────────────────────────┐
│ ChatView                                                            │
│ ┌───────────────────────┬────┬───────────────────────────────────┐ │
│ │ 对话（自适应剩余）     │刻度│ 图谱（可拖宽 280–560，可折叠）      │ │
│ │ 812 → 1000px          │40px│ 默认 380px                        │ │
│ └───────────────────────┴────┴───────────────────────────────────┘ │
│                                                                     │
│        ┌──────────────────────────────────────────┐                 │
│        │ DocumentPeek（页面级侧滑，48–58vw）        │  ← 独立图层      │
│        │ 不隶属于图谱面板，宽度与图谱无关           │     覆盖对话/图谱 │
│        │ 可拖拽调宽、可对比另一篇、支持选区复制     │                 │
│        └──────────────────────────────────────────┘                 │
└────────────────────────────────────────────────────────────────────┘
```

**三条规则**：

1. **图谱**是「空间参照物」——需要够大能看清结构，但可以折叠。宽度可拖、记忆在 localStorage。
2. **DocumentPeek** 是「阅读行为」——从右侧滑出，覆盖对话区（读文档时本就不在对话），宽 48–58vw，最小 520px。**不受图谱宽度限制**。
3. 两者**互不嵌套**。从图谱节点打开文档时，peek 覆盖在上层，关闭即回到图谱原位。

### 2.3 为什么不是其他方案

| 备选 | 否决理由 |
|---|---|
| 弹窗 | 遮住它正在回答的那个问题，且与你说的「廉价」一致 |
| 跳转到记录页 | 丢失当前上下文（在调试检索不该被扔走） |
| 图谱换成全屏 tab | 失去「对话时瞥一眼关联」的轻量价值 |
| 文档塞进图谱面板 | 340px 内读正文必然难读，这是问题本身 |

### 2.4 文档节点展示规则（图谱内）

当前所有文档节点同尺寸同标签，30+ 篇时成一团。改为**按度数分级**：

| 度数（被引用次数） | 显示 |
|---|---|
| ≥ 3 | 完整标签，半径加大 |
| 1–2 | 仅圆点，hover 出标签 |
| 0 | 折叠为「+N 篇」聚合节点，点击展开 |

这样「被引用多的文档」自然视觉突出——这本就是有意义的信号，而非人为强调。

## 3. 逐项方案

### 3.1 字体系统（P0，影响全局）

**问题量化**：11px 用 55 处、12px 用 38 处；全局 `-webkit-font-smoothing: antialiased` 在浅底小字上显著变细。

**改动**（`tokens.css` + `base.css`）：

| 令牌 | 现值 | 新值 |
|---|---|---|
| `--fs-2xs` | 11px | **12.5px** |
| `--fs-xs` | 12px | **13px** |
| `--fs-sm` | 13.5px | **14px** |
| `--fs-base` | 15px | **15.5px** |
| `--fs-md` | 17px | **18px** |
| `--lh-body` | 1.7 | **1.75** |
| `--lh-loose` | 1.9 | **2.0** |

**渲染**：移除全局 `antialiased`，仅对深色底（用户气泡、Toast、tooltip）保留，因为深底需要更细的渲染才不糊。浅底小字需要正常的次像素渲染才够清晰。

**硬规则**：`< 13px` 只允许时间戳、ID、徽章；连续阅读内容最小 14px。

### 3.2 记录页（P0，可用性倒退）

1. **滚动归属改为整页**：`.app-view` 加 `overflow-y: auto`，移除 `.results` 独立滚动
2. **筛选区可折叠**：默认收起为一行摘要 + 已选 chips，省 ~140px
3. **字号**：摘要 12→14px，详情 13→14.5px / 行高 1.85
4. **结果卡阅读优先**：标题 16px、摘要 3 行、keywords 降为次要

### 3.3 码字编辑（P0 修 bug，P1 拆语义）

| 项 | 改动 |
|---|---|
| 红线 | 焦点态去掉 3px 外扩阴影，只改边框色 |
| 专注模式 | 隐藏侧栏 + 真正居中 + 宽度 68ch→**76ch** |
| 保存语义 | 主按钮改「保存到笔记」；状态条拆 `草稿 12:03` / `已落盘 12:05`；Toast 明确「尚未进入知识库」 |
| 摘取面板 | 宽度 480→**560px**；候选可展开全文；支持**选中片段插入** |

### 3.4 DocumentPeek（P1，跨四入口）

新增 `components/document/DocumentPeek.vue` + `stores/peek.ts`：

- 页面级侧滑，48–58vw（min 520 / max 900），左缘可拖拽调宽
- weekly 按 problem / analysis / solution 分段展示；daily 显示正文
- 顶部：类型徽章、日期、来源路径；底部：复制全文 / 复制选中 / 在对话中追问 / 摘入周记
- 支持「对比另一篇」（并排两栏，P2）
- Esc 关闭，记住每篇的滚动位置

**接入点**：检索调试最终结果、检索调试逐阶段、检索调试文档列表、聊天引用 chip、记录页结果卡、图谱 Inspector。

### 3.5 展开项容器分级（P1）

| 场景 | 处理 |
|---|---|
| 检索调试日志 | 浅底 + 左侧 2px 语义色条（error 红 / warn 黄 / normal 灰） |
| 记录页结果卡 | 卡片式（浅底 + 圆角 + hover 抬升） |
| 流程日志 | 细左边框线，与检索调试一致 |
| 聊天执行链 | **保持无框**（消息附属信息，加框喧宾夺主） |

`AppDisclosure` 上下 padding 2px → 8px，相邻间隔 2px。

### 3.6 图谱（P2）

- 宽度可拖 280–560，默认 380，记忆在 localStorage
- 可折叠到 0，保留 6px 恢复条
- < 1100px 改为覆盖式抽屉（不再直接隐藏）
- 文档节点按度数分级（见 §2.4）

### 3.7 模型配置重构（P3，需动后端）

**思路**：把 `driver: ollama|api` 降级为**统一连接配置**。ollama 从 v0.1.24 起提供 OpenAI 兼容的 `/v1/chat/completions`，可收敛为同一协议。

```
Connection { id, name, base_url, api_key, kind: "openai-compatible" }
Model      { id, model_name, connectionId, temperature }
```

**界面**（抽屉内两段，避免复杂）：

1. **连接**：横向卡片列表（本地 Ollama / DeepSeek / 自定义），点击编辑
2. 每张连接卡：名称 + `base_url` + `key`（ollama 可空）+「拉取模型」按钮 → 下拉列表 **且保留手动输入**
3. **槽位**：small / large / chat 从已配置模型中选择
4. ollama 的「启动到显存」移入「高级」折叠区

**关键**：拉取模型列表必须**走后端代理**——浏览器直连会 CORS，且 key 不应暴露在前端请求中。

### 批次 D 实施记录

**设计思路：把 driver 降级为「连接」，但不改运行时**

原本 `driver: "ollama" | "api"` 是硬编码二元分支，两侧字段不通用（切换要清空对侧）。改为三层：

```
Connection { id, name, kind: "ollama"|"openai", base_url, api_key }
    ↓ 运行时翻译
SingleModel { driver, ollama_name | api_model_name, api_key, base_url, temperature }
    ↓ 原样使用
get_langchain_llm()  ← 保持不变
```

**关键决策：不改底层协议。**
ollama 虽提供 OpenAI 兼容的 `/v1/chat/completions`，但现有预处理/总结链路依赖 `ChatOllama`（含 keep_alive、`/api/ps` 显存管理）。强行统一会引入回归风险。所以统一的是**配置与交互形态**，不是底层调用——`kind` 只在运行时决定用哪个 LangChain 客户端。

**后端改动**

| 文件 | 内容 |
|---|---|
| `config/model_config.py` | 新增 `Connection` dataclass；`GlobalModel` 增加 `connections` 字段与 `upsert/remove/find/model_from_connection` |
| `api/connections.py`（新增） | `GET/POST/DELETE /connections` + **`POST /connections/models`（代理拉取）** |
| `api/tool.py` | `/tool/model` 返回值附带 `connections`（脱敏） |
| `main.py` | 挂载 connections 路由 |

**为什么拉取模型列表必须走后端代理**
1. 浏览器直连 `api.deepseek.com/models` 会被 CORS 拦截；
2. `api_key` 不应出现在前端请求头里（可被 DevTools 看到、被扩展读取）。

后端用自己持有的 key 代发请求，只回传模型名。

**前端改动**

模型抽屉从「三个槽位 × driver 切换 × 预设下拉」重做为两段：

1. **模型连接**：卡片列表（类型标签 + 名称 + 地址 + 「拉取模型」+ 编辑/删除）
2. **槽位**：显示当前模型 → 从已拉取模型中选择（按连接分组）**或手填模型名** → temperature
3. **高级 · Ollama 显存管理**：默认折叠

**实测**

| 项 | 结果 |
|---|---|
| 连接列表 | 本地 Ollama + DeepSeek，类型标签正确 |
| **拉取模型（真实网络）** | 从 DeepSeek 拉到 **2 个模型**（deepseek-flash、deepseek-v4-pro） |
| 槽位下拉 | 按连接分组填充，同时保留手填输入 |
| 高级区 | 默认折叠，展开正常 |
| Ollama 不可用时 | 「拉取失败：…连接被拒绝」，可读不崩溃 |
| 无障碍 | 0 违规（修了 `slot__kind` 一处 4.37:1 对比度） |

### 批次 F 实施记录：二轮反馈修复（2026-11-08）

用户复测后指出五个仍未修好的问题。**其中三个是我第一轮「声称修好但实际没修」的**，值得逐条记录根因。

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 编辑页左侧红线仍在 | 我第一轮只是把 3px 外扩 `box-shadow` 换成 2px `border-left`，**颜色仍是朱砂**——本质没变，只是细了。第二轮排查发现真正的元凶是 **`base.css` 的全局 `:focus-visible { box-shadow: var(--focus-ring) }` 命中了 CodeMirror 的 contenteditable**，导致正文区出现一圈朱砂描边 | ① 编辑器容器不再用朱砂描边，焦点只做背景微提亮；② 给 `.cm-content` 加豁免，不用全局焦点环（编辑器有闪烁光标已足够） |
| 2 | **「插入选中」根本没实现** | 两层原因：`insert()` 里仍是旧版本（早期一次重写覆盖了新逻辑）；且 `window.getSelection()` 在 `click` 事件触发时**已被浏览器清除**，实时读永远是空 | ① 重写 `insert()` 真正使用选区；② 在 `mouseup` 时把选区**缓存到 `capturedSelection`**，插入时读缓存。实测：选中 20 字 → 写入 20 字（此前写 1310 字全文） |
| 3 | 点某段的「从对话摘取」，插入目标不跟随 | 面板的 `target` 是面板内部状态，与触发按钮无关 | `WriteView` 记录触发来源段落，作为 `initialTarget` 传给面板并在打开时同步。实测：点 analysis 的按钮 → ②analysis 自动选中 |
| 4 | 文档侧滑面板太大、右侧大片空白 | 默认宽度按屏幕比例（50vw），1500px 屏 → 750px，而 62ch 正文只需 ~620px | 默认宽度改为**固定 620px**（min 420 / max 900），窄屏才铺满。实测宽度 750 → 620，正文占满无空白 |
| 5 | 侧滑面板需点击空白处收起 | 只有 Esc 与关闭按钮 | 加半透明遮罩，`mousedown.self` 关闭；并修复**路由切换时遮罩残留**导致点不动页面的问题 |

**另外发现并修复的两个 bug**

1. **`ResultCard` 的展开事件误绑到 peek** —— `@open="onOpenPeek"` 导致点一下展开卡片就弹出侧滑面板。已移除该绑定，只有「阅读全文」按钮触发 peek。
2. **`emptyOutDir: false` 与裸 `vite build` 冲突** —— 项目改为 `emptyOutDir: false`（规避 Windows rimraf ENOTEMPTY）并配套 `npm run clean:dist`；我此前用裸 `vite build` 导致 dist 为空，一度误判「页面缺 title」。**构建必须用 `npm run build` / `npm run build:fast`。**

**方法论教训**：「声称修好」不等于「验证修好」。红线问题连续两轮误判，是因为我只看了自己写的 CSS 声明（`border-left` 确实是暖灰了），却没去**遍历所有元素的 computed style 找真正的朱砂来源**。第二次改用全元素扫描后一次定位。

**回归**：70 个单测全绿；axe 五视图 0 违规；零控制台错误。

**标签分级为什么比「节点数阈值」更合理**

旧规则：节点 ≤24 时全显示标签，否则只显示会话与推理。结果是 30+ 篇文档时**所有文档标签消失**，用户看不到哪篇是哪个。

## 8. 批次 H：四轮反馈（2026-11-08）

### 8.1 清空内容后草稿仍被恢复

**现象**：写一段字 → 全删 → 切走再回来，删掉的内容又出现了。

**根因**：`persistDraft()` 开头是 `if (!isDirty.value) return`。
不脏就跳过写入 —— 于是「写过又全删」时，**旧草稿永远留在 localStorage 里删不掉**，下次进来照常恢复。

**修法**（三层都补）：
1. `persistDraft()`：内容为空时 **`clearDraft()`** 而不是 return
2. `watch`：清空到 0 字时立即清草稿，不等 2s 防抖
3. `restoreDraft()`：读到的草稿本身为空 → 视为无草稿并清掉（清理历史脏数据）

实测：删除后 `storage: EMPTY`，切回编辑器为空，无「已恢复草稿」提示。

### 8.2 专注模式无法滚动

**现象**：内容写满后底部被裁掉，页面与编辑器都滚不动。

**根因**：三层叠加 ——
- `body { overflow: hidden }`（全站基线）
- `.app-view` 与 `.editor-wrap` 都是 `overflow: visible`
- `.md-editor .cm-editor` 写死 `height: 100%`，CodeMirror 的 scroller 又是 `overflow: auto`

结果：外层不滚、内层高度被压死在容器内，超出部分直接裁切。

**修法**：
- `.app-view { overflow-y: auto }` —— 编辑页改为整页滚动
- 移除 `.editor-wrap` 的 `overflow-y: auto`，**只保留一个滚动宿主**（双层滚动会让滚轮行为取决于光标位置）
- `.cm-editor` 去掉 `height: 100%`，改 `min-height: inherit` + 内容自适应高度
- `.cm-scroller` 改 `overflow: visible`

实测：滚轮 0 → 500，PageDown → 662，内容高度 1562 > 视口 900。

### 8.3 保存语义仍然混淆

**现象**：专注模式点「保存」像没反应。

**根因**不是按钮失效，而是**保存后清空编辑器 + 只有一条转瞬即逝的 Toast**，用户看到的是空白编辑器，自然觉得"什么都没发生"。

**修法**：
1. **保存后保留内容**，只清草稿（保存 ≠ 清空）
2. 新增 `isPersisted` 状态：把当前内容指纹与保存时的快照比对，之后有改动就自动变回「未持久化」
3. 状态条三态明确：

   | 状态 | 显示 |
   |---|---|
   | 无内容 | 尚未填写 |
   | 有内容未保存 | ⚠ 未持久化 · 仅存于草稿 + 草稿时刻 |
   | 已保存 | ✓ 已持久化 HH:mm；未预处理时追加「未进入知识库」 |

4. 专注模式顶栏同步显示持久化状态，按钮文案改为「保存到笔记」

### 8.4 全局焦点环误伤输入框（两个 bug 的共同根因）

**现象**：主对话输入框聚焦时出现一整圈朱砂红框；编辑页左侧贯穿红线。

**根因是同一个**：`base.css` 的 `:focus-visible { box-shadow: var(--focus-ring) }`
—— `--focus-ring` 是「2px 白 + 2px 朱砂」双层描边，用于按钮/链接没问题，
但命中 `textarea` 与 CodeMirror 的 `contenteditable` 时就是一整圈抢眼的红框。

**修法**：把 `textarea / input / select / .cm-content` 从全局焦点环中豁免。
输入类元素有闪烁光标 + 各自的边框加深，已经足够指示焦点。

> 这一条连续三轮才定位：前两轮我只检查自己写的 CSS 声明（`border-left` 确实已经改了），
> 却没意识到有一个**全局规则在暗中覆盖**。改用「遍历元素扫 computed style 找朱砂色来源」
> 才一次锁定。教训：**别只看自己写的那条声明，要看最终生效的那条。**

### 8.5 文档侧滑宽度回滚

上一轮我擅自把默认宽度从 50vw 收窄到固定 620px —— 用户并未要求这个改动。已回滚为 50vw（min 480 / max 960）。

### 8.6 视觉层次：靠亮度而不是靠装饰

**问题**：界面暗沉困倦、层次弱。用户明确担心「盲目加背景点缀会主次不分」。

**诊断**（量了四层表面的 HSL）：

| 层 | 原色 | 饱和度 | 亮度 |
|---|---|---|---|
| sunken | `#ece4d3` | 40% | 88% |
| base | `#f4efe4` | 42% | 93% |
| card | `#faf6ec` | **58%** | 95% |
| overlay | `#fdfbf5` | **67%** | 98% |

关键发现：**越"高"的层反而越黄**（饱和 42% → 58% → 67%）。层次靠的是"更黄"而不是"更亮"，这是反的；大面积高饱和暖黄还会造成视觉疲劳。

另外两个被压得太轻的要素：
- `--border-soft` 与卡片底只差 2 个亮度点，几乎看不见
- `--ef-1` 阴影 alpha 仅 `.05/.06`，叠在米色底上等于没有

**层次 = 填充 + 边缘 + 阴影三者协同，当时只有第一项在工作。**

**修法（不加任何装饰）**：
1. **重排亮度阶梯**，越往上的层越接近纯白、饱和度递减
   base `#f7f2e8` → sunken `#efe8da` → card `#fffdf9` → overlay `#ffffff`
2. **锐化边缘**：`border-strong` `#cfc0a6`、`border` `#d9cdb6`、`border-soft` `#e6dcc8`
3. **加重阴影**：`ef-1` alpha `.05/.06` → `.07/.09`，色相从灰黑改为暖褐 `rgba(52,42,30)`
4. **减淡背景雾**：body 两层径向渐变从 `.05/.06` 降到 `.025/.02` —— 原来那层"雾"把卡片与底色的亮度差抹平了

结果：卡片真正浮起来了，不再是"贴"在页面上的感觉；整体也不再闷黄。

70 个单测全绿；axe 五视图 0 违规；草稿清理、页面滚动、焦点边框、持久化状态全部实测通过。

## 10. 批次 J：七轮反馈（2026-11-08）

### 10.1 输入框聚焦没有淡红响应

**根因**：`base.css` 的全局 `:focus-visible { box-shadow: var(--focus-ring) }`。
上一轮为了消掉「半圈突兀红边」，把 `.composer__box` 的聚焦样式整个删了 —— 但当时看到的那圈红
其实是**全局焦点环 + 自己的边框**两条叠在一起。删掉自己的边框后，焦点环对输入类的豁免还在生效，
于是变成「什么都没有」。

**修法**：只保留 `border-color: var(--accent-soft)`，不加任何阴影。看点明确又不喧宾。

实测：`border rgb(226,179,163)`、`box-shadow: none`。

### 10.2 总结后图谱不清空

**两层问题**：

1. `ChatView.onSummarize` 原先只调 `session.load()` —— **点了等于什么都没发生**（上一轮已修为真实调用）
2. 但即使调了真实接口，图谱**不会自动同步**：总结会归档当前会话、生成记忆节点，节点集合整体改变，
   而 `GraphCanvas` 只在挂载时 `load()` 一次

**修法**：
- `GraphCanvas` 抽出 `syncFromStore()`，加 `watch(() => graph.nodes.length, syncFromStore)` 作为兜底
- `onSummarize` 成功后 `Promise.allSettled([session.load(), graph.load(), turnStore.loadReferenceData()])`

另修一个竞态：store 更新早于画布尺寸就绪时，物理引擎画在 0×0 上。`syncFromStore()` 在尺寸未就绪时
走 `requestAnimationFrame` 重试，而不是静默失败。

实测：对话后 7 API / 7 DOM 一致；总结后 1 / 1（会话归档，只剩新记忆，符合预期）。

### 10.3 滚轮缩放一步到顶

**根因**：一次滚轮事件直接 `viewScale *= 1.15` 并吃满整个 delta，鼠标滚一格就跳 15%。

**修法**：指数映射 + 单次夹紧。

```ts
const delta = e.deltaMode === 1 ? e.deltaY * 16 : e.deltaY   // 行模式换算成像素
let factor = Math.exp(-delta * 0.0012)
factor = Math.min(1.1, Math.max(0.9, factor))                 // 单次最多 ±10%
```

指数映射的好处是**快滚和慢滚的手感一致**——delta 大时因子线性拉长，但不会突变。

实测：连续 6 次滚轮 106% → 113% → 120% → 127% → 135% → 143%，过渡连续。

### 10.4 引导模式的占位符

**现象**：刚切到「引导咨询」、还没开始对话时，输入框就提示「回答引导者的问题…」——
但此时引导者根本还没提问。

**修法**：`guidedStarted = isGuided && guidedPairCount > 0`。没有问答对时用通用占位符。

实测：引导模式 + 0 轮 →「说点什么…」。

### 10.5 图谱光晕

原先是实心 `currentColor` 填一个 `r=2.1` 的圆 —— 直接把图形细节盖住了，看起来像一团粉块。

改为**径向渐变**（`svg-renderer.ts` 新增 `buildDefs()`）：

```
0% → alpha 0     （中心完全透明，不遮图形）
55% → 0.05
80% → 0.55
100% → 0
```

半径收到 `1.55`，hover 时才 `--halo-opacity: 0.1` 淡入。图形本身保持清晰，光晕只是描边外的一圈柔光。

> 说明：图谱字形当前是**混合实现** —— 会话用整枚 SVG 图像（`image.href` → `/brand/graph/session-orbit.svg`），
> 记忆 / 文档 / 推理仍是用 `parts` 路径绘制的「心迹生长」几何（轨道环、枝蔓、卷边纸片、纸飞机）。
> 这与我此前 `graph_glyph_system.md` 里写的「踪迹语言」纯线方案不同，该文档已标记为未采用的备选设计。
> 本轮按用户指示只修光晕，不动字形。

### 10.7 补记：光晕的两个连环 bug（自查发现）

10.5 写的「改成径向渐变」当时**并没有真正生效**，两次自查才发现：

**① 渐变是死代码**

```ts
halo.setAttribute('fill', 'url(#gnode-halo-grad)')   // 表现属性
```
```css
.gnode__halo { fill: currentColor; }                  // CSS 规则
```

CSS 声明**永远**覆盖 SVG 表现属性。所以 `fill` 恒为 `currentColor`，
光晕从始至终都是实心圆——我上一轮"改好了"的渐变一次都没渲染过。

验证方式：hover 时读 `getComputedStyle(halo).fill` 与 `<stop>` 数组 —— 渐变节点存在，
但实际填充不是 `url(...)`。这正是「别只看自己写了什么，要看最终生效的是什么」的再次应验。

**② 会话节点根本没有光晕**

```css
.gnode--image .gnode__halo { display: none; }
```

这行是纯色圆时代的补丁（怕叠出粉盘）。但它连带关掉了会话节点的**全部 hover / 选中反馈**，
看起来像交互坏了。

**修法**：改用 **mask**，不用渐变填充。

```ts
// 实心圆 + CSS 上色（currentColor 按类型取色，暗色免重绘）
halo.setAttribute('mask', 'url(#gnode-halo-mask)')

// 遮罩：中心 alpha=0，62% 处 0.1，82% 处 0.75，边缘 0
maskEl.setAttribute('maskUnits', 'objectBoundingBox')
maskEl.setAttribute('maskContentUnits', 'objectBoundingBox')
```

mask 是独立属性，不会被 `fill` 规则顶掉；`objectBoundingBox` 让遮罩随圆半径自动缩放，
调 `r` 不用重算渐变。

同时删掉 `.gnode--image .gnode__halo { display: none }`，改为按档给半径（1.25 / hover 1.45 / active 1.55）。
半径是从实测推的：字形最大约 `0.79r`，光晕亮带在 `~0.82 × r`，所以 `r=1.25` 时亮带落在字形外缘，
既成环又不盖细节。试过 `1.95`，亮带跑到字形外面很远，又变回粉盘。

### 10.8 补记：Inspector 在窄面板下挤没画布

图谱面板默认 380px、可拖到 280px，而 Inspector 固定 `width: min(280px, 78%)`。
380px 面板打开 Inspector 后**画布只剩 100px**，看起来像样式坏了。

这不是新问题，是「文档阅读被塞进小容器」的同类——根因都是**子面板按绝对尺寸设计，
不考虑容器实际宽度**。

**修法**：给 `.graph-pane` 加 `container-type: inline-size`，用容器查询分档：

| 面板宽度 | Inspector 行为 |
|---|---|
| ≥ 460px | 侧栏，`min(300px, 72%)` |
| < 460px | 覆盖整个面板当抽屉（`width: 100%`） |

**为什么按容器宽度而不是视口宽度**：面板宽度是用户拖的，与视口无关。
同一块 1500px 屏幕上，面板既可能是 280px 也可能是 560px，媒体查询判断不了。

另外：会话节点当前 `id`、`summary`、关联全为空（后端只在有对话后才填），
Inspector 只剩标题和类型徽章。已把空 `id` 行加 `v-if` 去掉——空壳至少不该有一行空白乱码位。

### 10.9 补记：验证脚本的基础路径

`audit-a11y.cjs` 默认扫 `http://127.0.0.1:8010/next/`，但新版前端已改挂根路径。
访问 `/next/` 返回 404 → Playwright 停在错误页 → **axe 扫出来 0 违规，是假的**。

**修法**：

负向验证：`VERIFY_BASE=.../next/ node scripts/audit-a11y.cjs` 现在会正确报错而不是假绿。

### 12.3 「小细字看不清」的真正根因（三个叠加）

用户点名了三处：码字编辑的「9 字 · 约 1 分钟 · 填写 2/3」、流程日志的
「共 4 条 · 版本 0 · 仅累积新增…」。彻查后发现**不是单一原因**：

**① 中文落进等宽栈**

```css
--font-mono: 'JetBrains Mono', 'SFMono-Regular', Consolas, monospace;
```

JetBrains Mono 没有汉字字形，中文会落到最后的 `monospace` 兜底 —— 那是
系统默认的等宽中文字体，笔画细、字重轻。而「0 字」「约 1 分钟」「共 8 条 · 版本 16」
全都套在 `.meta-bar` / `.hint` 这类 mono 元素里。

**修法**：在 mono 栈中间插入无衬线 CJK。

```css
--font-mono: 'JetBrains Mono', 'SFMono-Regular', Consolas,
  'Noto Sans SC Variable', 'Noto Sans SC Fallback', 'PingFang SC', 'Microsoft YaHei', monospace;
```

英数仍由 JetBrains Mono 渲染（等宽对齐全保留），中文回落到与正文一致的字体。

**② 大量地方绕过令牌写死 9.5–12.5px**

令牌下限本来定在 12.5px，但 20 个文件里散落着 `font-size: 9.5px` / `10px` / `10.5px` /
`11px` / `11.5px` / `12px` 这类硬编码，绕过了「< 13px 只允许时间戳/ID/徽章」的规则。

**修法**：全部归到 `--fs-2xs`，并把令牌本身再上调一档：

| 令牌 | 旧 | 新 |
|---|---|---|
| `--fs-2xs` | 12.5px | **13px** |
| `--fs-xs` | 13px | **13.5px** |
| `--fs-sm` | 14px | **14.5px** |

**③ 可读中文被当成「三级灰小注」处理**

三处最典型的对比：

| 位置 | 内容 | 原 | 新 |
|---|---|---|---|
| 流程日志 `.hint` | 「共 16 条 · 版本 16 · 仅累积新增…」 | mono 12.5px 三级灰 | sans 14.5px 次要色 |
| 码字编辑 `.meta-bar` | 「26 字 · 约 1 分钟」 | mono 12.5px 三级灰 | sans 14.5px 次要色 |
| 检索页 `.rank__sum` | 文档摘要正文 | 10.5px 三级灰 | 13px 次要色 |

判据：**这行字是给人读的句子，还是 ID/数字/徽章**。前者一律按正文辅助文字对待
（sans + 次要色 + `--fs-sm`），后者才允许更小。

### 12.6 关于「Noto Sans SC Thin」

CDP 的 `CSS.getPlatformFontsForNode` 对同一元素返回 `Noto Sans SC Thin`。
一度怀疑可变字体的字重轴没生效，用 100/300/400/500/700/900 六档行做视觉对照后
确认**字重轴正常**（400 与 900 笔画粗细差异明显）。`Thin` 只是字体 name 表里的
默认字族名，CDP 报的是该族名而非实际字重实例。

教训：CDP 报的字体名不等于渲染字重，视觉对照才是判据。

## 13. 批次 M：四轮修复（2026-11-08）

### 13.1 用户气泡：淡黄保留块面

上一轮读错了意图（以为是"不要块面"，改成了完全透明）。实际是**保留气泡、只淡一点**。

```css
--surface-user: #f6ecd0;   /* 淡黄 */
--border-user:  #ecdcb8;   /* 几乎看不见的边 */
```

无阴影。与页面底对比 1.06:1 —— 能认出气泡，但视觉重量明显低于建议者的白卡（1.16:1，
带边框 + `ef-1` 阴影）。正文对比 13.15:1。

### 13.2 刻度轨定位不准

**现象**：点第 1 轮，落到的却是第 3 轮。

**根因**：`scrollIntoView({ block: 'center' })` 按**整轮**居中。实测单轮高度
1000–3300px，而滚动视口只有 392px（1280×720 窗口）。按整轮中心对齐，等于把
轮次开头推到视口上方 1134px 处 —— 用户看到的是轮次中后段，也就是下一两轮的内容。

**修法**：改为把轮次**顶部**对齐到视口留白处，自己算偏移量。

```ts
const TOP_PAD = 12
const top = el.getBoundingClientRect().top - root.getBoundingClientRect().top + root.scrollTop
root.scrollTo({ top: Math.max(0, top - TOP_PAD), behavior: 'smooth' })
```

实测：点第 4 个刻度 → 视口顶部正是第 4 轮（偏移 23px）。

顺带记一个坑：调试时曾误判"点击无效"，因为回复还在流式输出，
`followIfNearBottom` 的 120ms 定时器把页面又拉回底部了。
**测滚动类交互必须在流式结束、页面静止后测。**

### 13.3 悬停预览固定在顶部

**现象**：鼠标停在第 12 个刻度上，摘要浮层却出现在轨道最上方，中间隔了十几行。

**根因**：`.rail-ticks__tip { top: var(--sp-2); }` 是写死的。

**修法**：`showTip()` 在 mouseenter/focus 时算出刻度中心相对轨道的偏移，写入
inline `top`，CSS 用 `translateY(-50%)` 垂直居中到刻度上。

```ts
hoveredTop.value = Math.min(Math.max(center, 28), Math.max(28, rr.height - 28))
```

首尾刻度会被夹进轨道范围，避免浮层跑出可视区。

注意：入场动画只能改 opacity。若改 transform 会覆盖 `translateY(-50%)`，浮层会跳位。

实测：刻度中心 221 → 浮层中心 221；323 → 323。完全对齐。

### 13.4 LLM 返回不存在的引用

**现象**：回复里出现一个引用角标，悬停显示「引用 · 无」，点了没反应。

**根因**（实测抓到的真实数据）：

```
referencedDocIds: [5dc4aa0c…, 97b00e4e…, fb59849c…]
citeMarks:        […真实 ID…, { id: "无" }, { id: "无" }, { id: "无" }]
```

模型输出了 `[[cite:无]]`。来源是 RAG prompt 里的这句：

> `# 用户主动引用的资料（可选；若为「无」则忽略）`

模型把「无」当成了一个合法 ID 抄进标记。这属于**提示词措辞诱导的格式错误**。

**修法（两层）**：

**① 前端防御**（`core/domain/citations.ts`）

```ts
const PLACEHOLDER_IDS = new Set(['无','（无）','(无)','未引用','none','null','n/a','-','—'])
export function isValidCiteId(id) { ... }
```

`extractCitations` 跳过占位符；`tokenizeInline` 对占位符**整个丢弃、不产生 token** ——
既不出角标，也不把字面量留在正文里。

**② 提示词收紧**（`config/prompt_config.py`）

- 引用规范新增第 4 条：禁止把占位词写成 ID，没有可引用内容时整段不写标记；
- 两处 `{attached_context}` 的标题改为「此段若为「无」表示没有附件，直接跳到下一节，
  不要把它当作引用内容」。

**为什么要两层**：前端防御保证已有的历史数据与任意模型输出都不会露出幽灵角标；
提示词收紧从源头减少此类输出。只做一层都不够 —— 提示词无法保证 100%，前端不修则历史消息仍然显示。

### 13.5 过往记录：两条检索链路互相污染

**现象**：在「知识文档检索」里选中「预处理」，再切到「历史记忆检索」，
记忆页仍显示预处理说明、整块筛选区消失、按钮写着「运行预处理」；
而且两条链路共用一个 `searched` 标志，切 tab 就把它重置了 ——
「已按条件筛选」标识随之消失。

**根因一**：`isPreprocess` 没判断 tab。

```ts
// 旧：isPreprocess = records.knowledgeMode === 'preprocess'
const isPreprocess = computed(() => isKnowledge.value && records.knowledgeMode === 'preprocess')
```

`knowledgeMode` 是知识文档的二级模式，不该在记忆页生效。

**根因二**：`filter` / `searched` / `results` 两个 tab 共用一份。

在知识文档筛过一轮再切到记忆页，筛选条件还留着（语义并不通用）；
切回来时 `searched` 已被重置，看起来像从没检索过。

**修法**：按 tab 各存一份状态。

```ts
interface TabState {
  filter: RecordsFilter
  vectorQuery: string
  searched: boolean
  results: (Document | Memory)[] | null   // null = 未检索，回落到全量
  error: string | null
}
const states = ref<Record<RecordsTab, TabState>>({ knowledge: …, memory: … })
```

对外的 `filter` / `vectorQuery` / `searched` / `error` 改成**读写当前 tab 那一份**的
computed，视图层的双向绑定代码一行没改。

实测（知识页筛「内耗」→ 记忆页筛「焦虑」→ 切回知识页）：

| 步骤 | 标识 | 计数 | 已选 chip | 关键词 |
|---|---|---|---|---|
| 知识页检索后 | 已按条件筛选 | 4 条 | 词 内耗 | 内耗 |
| 切到记忆页 | 无 | 10 条 | — | — |
| 记忆页检索后 | 已按条件筛选 | 2 条 | 词 焦虑 | — |
| 切回知识页 | **已按条件筛选** | **4 条** | **词 内耗** | **内耗** |
