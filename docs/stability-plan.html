问题清单（按严重度分级）

P0 · 架构级 —— 影响可用性与数据正确性

P0-1并发会话状态全局单例，无并发保护、无会话隔离core/meta_db/context_meta.py · api/chat.py · api/state.py
证据：SESSION_STATE 为进程级单例（id=1 唯一约束），所有请求共享 full_chat_history / guided_reasons / similar_memories / referenced_doc_ids；agent_service_entry 读改写无锁；SSE 把同步入口丢进线程池，并发聊天会互相覆盖会话状态。
修复方向：最小侵入：全局 threading.RLock 包住会话读写与 save_state；再进一步按 session_id 做映射隔离（多会话各自独立状态）。
P0-2缓存知识/记忆缓存为启动快照，运行期永不刷新core/helper/knowledge_cache.py · memory_cache.py · core/tools.py
证据：KNOWLEDGE_CACHE / MEMORY_CACHE 在 import 时一次性加载；summarize_memory() 写入新记忆后不更新 MEMORY_CACHE，网页"历史记忆"查不到刚总结的内容直到重启；save_daily/weekly 只写源 .md，新文章不进检索库；/preprocess 跑完全流程也不回填内存缓存。与已修的 LLM 缓存是同一类架构债。
修复方向：为两个缓存增加 reload()，在 summarize / preprocess / save 成功后统一回填；所有"写入后生效"的入口收敛到同一刷新函数。
P0-3异常LLM 调用链无统一异常兜底，一次失败全链路 500core/agent.py · core/helper/RAG_agent.py · core/tools.py
证据：agent_executor.invoke、_is_counseling 预分类、RAG_agent.chat、guided_reasoning、_auto_advise 全部裸调 LLM；模型 API 超时/报错即抛异常 → catch_exception 返回 500 服务内部异常: … 直出给前端（用户已多次见到）。预分类失败时也没有降级路径。
修复方向：LLM 封装增加超时 + 一次性重试；各入口 try/except 返回结构化错误；_is_counseling 失败降级为直接走 counseling 而非中断请求。
P0-4流式SSE 是"伪流式"：先全量阻塞再逐字播放，错误不可见api/chat.py:22-47 · api/trace.py:25-38
证据：/chat/stream 的 generator 无 try/except，agent_service_entry 抛错时流直接断开、前端收不到任何错误事件；GLOBAL_TRACKER.clear_trace() 在生成器内执行，并发下互相清空；回答并非真正的逐 token 生成，延迟无改善。
修复方向：SSE 全程 try/except 并推送 error 事件；clear 移到请求开始前；后续可选接入 LLM stream 实现真流式。
P0-5数据文档字段假设脆弱：emotion 缺键 / summary 非文本即崩core/meta_db/knowledge_meta.py:141-143 · core/helper/RAG_agent.py:30,44
证据：doc.emotion["primary"] / ["intensity"] 直接下标访问；document_loader 失败仍返回 {}（dict）混入缓存，下游 doc.summary 触发 'dict' object has no attribute 'summary' —— 与历史故障同根的另一条未堵路径。
修复方向：全部改 .get() 兜底；load_document 失败返回 None 并过滤（knowledge_loader 已修，document_loader 对齐）。

P1 · 健壮性 —— 影响一致性与资源占用

P1-1存储sqlite 无 WAL / busy_timeout，并发写可能锁库core/meta_db/*.py（4 处 _get_conn）
证据：每次操作新建连接、check_same_thread=False、无 busy_timeout、默认 journal 模式；SSE 线程池 + 定时总结并发写时有 database is locked 风险。
修复方向：统一连接工厂：PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;；写操作包事务。
P1-2一致性多步持久化无事务：总结/预处理中途失败即数据不一致core/tools.py summarize_memory · api/tool.py /preprocess
证据：summarize_memory 写 JSON → 向量库 → 元数据库三步，任一步失败留半套数据；/preprocess 全量重建无回滚，失败时新旧混杂。
修复方向：按"文件先行（可恢复）→ 向量/元数据尽力同步 + 失败告警"排序；preprocess 用临时目录替换 + 完成后刷新缓存。
P1-3增量preprocess 遇已存在 JSON 直接跳过：源文档更新不生效core/helper/preprocessor.py:143-149
证据：os.path.exists(target_json_path) 即跳过，无 mtime/hash 比对；用户修改 Daily/Weekly 的 .md 后，知识库内容永远是旧版。
修复方向：记录源文件 mtime/hash，变更才重处理；同时校验 date 字段生成逻辑（当前代码对 daily 的 date 处理有隐患，见 P2-3）。
P1-4资源trace 日志无限增长 + SSE 每 0.4s 全量轮询core/helper/trace_tracker.py · api/trace.py:25-38
证据：/trace/stream 对每条长连接每 0.4s 全量拷贝 get_all_trace()，trace 列表无上限；clear_trace 后 last_index 失配导致该连接永久断更。
修复方向：trace 环形上限（如 500 条）+ clear 后 SSE 重置游标；前端只拉增量。
P1-5配置main.py 硬编码 reload=True + 静态目录相对路径main.py
证据：uvicorn.run(reload=True) 在文件变动时重启进程（历史故障诱因之一）；StaticFiles(directory="web") 依赖工作目录，从其他路径启动即前端 404。
修复方向：reload 由环境变量/CLI 控制（开发默认开、运行默认关）；静态目录用 BASE_DIR/web 绝对路径。
P1-6数据检索召回面窄：BM25 只索引标签、向量库只存向量不存文本core/helper/BM25.py:41-57 · core/vector_db/documents_vector_db.py:58-61
证据：BM25 语料 = topic×3 + keywords×1（正文词召回不到）；chroma upsert 未传 documents/metadatas，检索结果全依赖 KNOWLEDGE_CACHE 反查，缓存过期即结果错位。
修复方向：BM25 语料加入 summary/content 分词；向量库写入时附带 documents，反查失败时可直接用库内文本兜底。
P1-7安全保存文章文件名未清洗，存在路径穿越api/tool.py save_daily / save_weekly
证据：custom_filename / filename 直接拼 DAILY_DIR / file_name，传入 ..\evil.md 可写出目标目录。
修复方向：只取 os.path.basename 并限制字符集；限制内容长度。
